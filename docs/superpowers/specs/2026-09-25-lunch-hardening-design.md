# Lunch: защита админки и улучшение проверок и загрузки

## Цель

Исправить обнаруженные проблемы в текущих потоках приложения Lunch: закрыть серверные операции админки, убрать ошибку строгой типизации, расширить автоматические проверки, уменьшить начальную загрузку фронтенда и не писать содержимое заказов в логи. Сохранить текущие пользовательские сценарии оформления и просмотра заказов.

## Наблюдения

- Авторизация Омска частично проверяется сервером через `x-admin-code`, но код хранится в `localStorage`; удаление заказов Омска не использует серверную проверку.
- Проверка доступа к админке Петербурга в `App.tsx` доверяет наличию значения в `localStorage`. Административные записи для Петербурга и общих городов не защищены middleware.
- Общая форма входа сравнивает код в клиентском коде через `VITE_ADMIN_CODE`.
- `npx tsc --noEmit` завершается ошибкой TS18048 на `orderDateBlock.message`; Vite build сам по себе эту проверку типов не выполняет.
- Vitest включает 19 тестов в двух файлах: тестируется логика случайного заказа и экспортных сумм, но нет проверок серверной авторизации.
- Маршруты всех городов и админок статически импортируются в `App.tsx`. Production build формирует JS-файл 629.88 kB и sourcemap 3,064.96 kB.
- `src/database.ts` пишет в консоль весь объект создаваемого заказа.
- `rollupOptions.external: ['xlsx']` не соответствует фронтенд-импортам: `xlsx` импортируется сервером, а экспорт в браузере загружает библиотеку отдельно.

## Рассмотренные варианты авторизации

1. Оставить код в `localStorage` и передавать его серверу для каждого административного запроса. Это минимальный патч, но код остаётся доступен клиентскому JavaScript.
2. Выдавать короткоживущую подписанную `HttpOnly` cookie после проверки существующего кода доступа. Этот вариант выбран пользователем: код не хранится в `localStorage` и не встраивается в клиентскую сборку.

## Дизайн

### Административная сессия

- Сохранить существующие коды и области доступа: отдельный код Омска и общий код Петербурга/прочих городов.
- Задать коды только на сервере через `OMSK_ADMIN_CODE` и `GENERIC_ADMIN_CODE`. Старый fallback на `VITE_ADMIN_CODE` отключён, поскольку `VITE_`-переменные могут попадать в клиентскую сборку; при переносе конфигурации общий код нужно выставить как `GENERIC_ADMIN_CODE`.
- Успешная проверка кода на `/api/omsk/admin/verify` или `/api/admin/verify` создаёт ограниченную по времени подписанную cookie. Запрос проверки без кода подтверждает существующую cookie.
- Ограничивать перебор кодов входа: не более 10 ошибочных попыток на область админки и IP клиента за 60 секунд, с ответом `429` и `Retry-After`; IP получать через Express только за доверенным proxy. По умолчанию доверять loopback proxy; дополнительные доверенные адреса явно задаются через `LUNCH_TRUST_PROXY`.
- Использовать отдельные имена cookie для Омска и общей админки. Cookie имеет `HttpOnly`, `SameSite=Strict`, `Path=/`, срок действия 8 часов и атрибут `Secure` в production.
- Подписывать сессию HMAC-ключом, созданным на старте единственного backend-процесса. Хранить активные сессии на сервере для проверки области доступа и отзыва при выходе. Перезапуск backend завершает сессии; текущий PM2-конфиг запускает один backend instance.
- Удалить секрет из клиентской проверки входа. Страницы входа передают код серверу только при входе; клиентские guards проверяют cookie через сервер.
- Применить middleware к административным изменяющим маршрутам, включая удаление заказов Омска, Петербурга и общих городов, изменение меню/периодов/отключённых дат, операции расширения периода и Excel-экспорт Петербурга.
- Сохранить публичными чтение меню и создание заказа сотрудником. Не менять цены или бизнес-правила заказа. Добавить nullable поле хеша токена отмены во внутреннее хранение SQLite/JSON; публичная форма заказа остаётся прежней.
- Текущая общая лента заказов остаётся публичной для сотрудников, поэтому имена, подразделения и состав заказов доступны анонимному чтению. Это сохранённое ограничение UX; для закрытия нужен отдельный пользовательский вход или изменение модели доступа.
- Сохранить сотруднику отмену собственного заказа: при создании сервер выдаёт случайный токен отмены один раз, сохраняет только его хеш, а клиент хранит токен для этого заказа и отправляет его в заголовке при отмене. API чтения заказов не возвращает хеш. Активная админская cookie разрешает удаление любого заказа; заказы без токена отменяются только администратором.
- Добавить серверный выход, который отзывает активную сессию и очищает cookie.

### Проверки и тесты

- Уточнить вычисление информации о блокировке дат так, чтобы TypeScript мог доказать безопасность чтения сообщения и логика не вычислялась несколько раз в одном render.
- Добавить `typecheck` script с `tsc --noEmit`.
- Добавить тесты с реальным auth middleware для отсутствующей, неверной, просроченной и корректной сессии, а также проверки административного запроса без доступа и с доступом. Отдельно подтвердить, что публичный маршрут создания заказа остаётся доступным.
- Проверить, что токен отмены не попадает в списки заказов, не позволяет отменить другой заказ и хранится только в хешированном виде на сервере.
- Запускать существующую Vitest suite, typecheck и production build после изменений.
- Полный production gate проверяет размер входного JS (<500 KiB), наличие lazy chunks и отсутствие sourcemap по умолчанию. `GENERATE_SOURCEMAP=true` включает sourcemap только для диагностической сборки.

### Производительность и сборка

- Использовать загрузку маршрутов по требованию для отдельных городских приложений и административных страниц с существующим UI fallback во время загрузки.
- Не выпускать публичные sourcemap в обычной production-сборке; оставить возможность включить их отдельной явной настройкой для диагностических сборок.
- Удалить неиспользуемое правило external для `xlsx`.
- Проверить результат сборки: городские/admin chunks должны быть разделены, а обычный входной chunk должен стать меньше текущего.

### Логи

- Удалить логирование целого заказа из слоя базы данных. Если диагностические сообщения нужны, оставлять только технические поля без имени, отдела и состава заказа.

## Область изменений

Ожидаемые файлы: `server.js`, `src/server/*` и их тесты, клиентские guards и формы входа, `src/App.tsx`, `src/components/OmskOrderForm.tsx`, `src/database.ts`, `vite.config.ts`, `package.json`, а также типы окружения. Не менять UI заказчика, формат данных в SQLite/JSON и логику цен.

## Критерии готовности

1. Без активной cookie административные изменяющие API возвращают 401; с подходящей cookie легитимная операция работает.
2. Проверки входа и выхода работают для Омска и общей админки; коды больше не хранятся в `localStorage` и не сравниваются в клиентском bundle.
3. Сотрудник по-прежнему может отправить заказ без административной cookie.
4. Vitest проходит, `npx tsc --noEmit` проходит, production build проходит.
5. Маршруты собираются в отдельные chunks, публичный production sourcemap не генерируется по умолчанию.
6. В логах больше нет полного содержимого заказа.

## Ограничения и риски

- Поскольку сессии и лимиты попыток хранятся в памяти одного backend процесса, его перезапуск завершает сессии и сбрасывает лимиты. При переходе к нескольким backend instances понадобится общее хранилище сессий/лимитов и общий signing secret.
- Существующие заказы не имеют токена отмены и после выпуска этой версии смогут удаляться только администратором; новые заказы можно отменять с устройства, с которого они были оформлены.
- Эта работа не меняет способы хранения заказов для городов и не добавляет авторизацию к публичным операциям оформления заказа.
